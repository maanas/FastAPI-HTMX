# A new or changed model

Only when the page owns data that no model holds yet.

1. Model in `app/models/<name>.py` on `Base` from `app.database.base`. `app/models/users.py` (`Role`)
   is the pattern for columns and ids.
2. Import it in `init_models` in `app/database/base.py`, with `# noqa: F401`. Without this Alembic
   does not see the table.
3. `.venv/bin/alembic revision --autogenerate -m "add <name>"`.
4. Read the generated file in `app/migrations/versions/`: the columns and constraints are what you
   meant, nothing else is dropped or altered, and a custom column type has its import at the top
   (the autogenerated file can miss it, see `TODO.md`).
5. `.venv/bin/alembic upgrade head`, then `.venv/bin/alembic downgrade -1` and `upgrade head` again
   to prove the downgrade works.

## Rules

- Never edit a migration that has been applied or committed; add a new one.
- One migration per step, committed with the model change.
- A column added to a table with rows is nullable or has a server default.
- A rename is an explicit `op.alter_column` / `op.rename_table`; autogenerate writes it as drop
  plus add, which loses the data.
- Load the `database-migrations` skill for anything beyond adding a table or a nullable column, and
  ask the director for the `database-reviewer` agent on a schema that other pages read.
